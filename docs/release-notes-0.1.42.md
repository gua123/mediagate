### 4 的根因：抽一帧太慢，慢一步就等于"没有"

原来的做法是把视频数据包装成 `MediaDataSource` 交给系统的 `MediaMetadataRetriever`——
它只能通过 `readAt` 一点点问数据，**本地大文件也要绕一大圈**；滑动手势要求即时反馈，
等你手指抬起来它还没抽出来，HUD 早就关了 ⇒ 你看到的就是"没有预览图"。

这一版的修法：

1. **本地文件直读**：`File` 真实存在时直接把**文件路径**交给 MMR（内部走 `MediaExtractor`，快一个量级）；
2. **拿不到就回退**：直读失败（返回 null）自动回到原来的数据源路径，不会因为走了新路而丢功能；
3. **相邻桶预热**：抽到一帧后顺手把前后各一个 5 秒桶也抽好（**只对本地文件做**，远端不白拉流量），
   下一次拖动几乎瞬时；
4. **如实告知**：还没抽出来时 HUD 显示「**预览生成中…**」，不再让界面看起来像坏了。

### 3 的说明（为什么"多线程"救不了）

< 1 MB/s ≈ **8 Mbit/s**，这基本是**家庭宽带上行 / 反向代理 / VPN 那一段**的速度——
客户端再怎么并发也变不出带宽（并发只能在"单连接被人为限速"时才有用，你这次实测没改善，
说明瓶颈不在连接的并行度上）。**内网没问题**也印证了这一点。
想让我把 **段大小 / 并发数** 做成设置项（你自己试着调）也可以，说一声就加。
