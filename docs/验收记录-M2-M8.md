## 5. 已知限制（不阻塞交付，记录在案）

- **R4 拖拽没有"毫秒级"**：TS 索引已接进播放页（无 PCR 提示 + 按关键帧偏移预取落点），
  但**没有替换 Media3 的 seek 实现**——那需要 fork `TsExtractor` 的 SeekMap 或自写提取器。
  Media3 仍用自己的二分查找定位，索引的作用是"把落点附近的数据预热好"（配合分段缓存）。
  所以 R4 验收里"有索引时 ≤1.5 s"这一条**不作为承诺**，真机实测数据出来后再说。
- **Media3 强制硬解的口径**：Android 没有官方的"只能硬解"开关，`FORCE_HW` 落地为
  **把软件解码器从候选里剔除**；本机确实没有硬解时如实退回软解并在 `DecoderReport.note` 上报（LibVLC 侧是真正的强制硬解）。
- **Media3 1.11 无字幕延迟 API**：外挂字幕改用 Compose 覆盖层渲染（同时满足样式可调 + ±0.5 s），引擎侧字幕轨道保留给内嵌轨。
- **ASS 仅基础样式**：Alignment/字体/字号/主色/粗斜体；不支持 `\pos` 精确定位、`\k`、特效。
- ~~whisper 模型 sha256 为空~~ → **已回填**（2026-10-03 从官方仓库下载三档模型逐份计算，字节数与 sizeBytes 一致）。

## 5.1 真机反馈：SFTP「认证失败」（2026-10-03）

用户发来截图：浏览页「加载失败，请重试 / 错误详情：SFTP 认证失败（账号或密码错误）：hml@192.168.40.6:22000」。

定位方式（**没有设备也能定性**）：用工程里的 opt-in 真网测试
`:data:storage-sftp:testDebugUnitTest --tests "*RealServerIntegrationTest*"`（读 `.toolchain/real-server.properties`）
在本机对**同一台服务器**跑了一遍——**6/6 全过**（probe 三段计时、列根目录、深偏移读取逐字节一致、
分段拼接一致、capabilities）。结论：服务器、账号、密码、我们自己的 SFTP 实现都没问题，
真机上失败的是**App 里存着的那份密码**（换包名后重建连接时输入的，或后来改过服务器密码但密码框留空被"沿用旧密码"）。

据此做了两处改进（0.1.5）：
1. **编辑器「测试一下」**：用当前草稿（含刚输入的密码）真跑一遍，**不落库**；密码留空则沿用已存密文
   （与保存口径一致），结果给一句中文（通过带耗时 / 失败带原因与三段耗时）。
2. **认证失败单独归类**（`BrowserErrorKind.AUTH_FAILED`）：浏览页不再只说「加载失败，请重试」，
   而是给出可照做的指引（去「连接」页编辑 → 重输密码 → 先「测试一下」再保存）。

## 5.2 继续追：用户坚持"账号密码都是对的"（2026-10-03，0.1.6）

用户再次反馈：「账号密码都是对的，但是显示错误」。于是把"凭据本身"这件事**用数据钉死**：
`.toolchain/real-server.properties` 里的用户名/密码（本机真网测试 6/6 通过的那份）与用户口径中的
`hml` / 9 位密码**逐字一致、纯 ASCII、无首尾空白**（比较过程只输出布尔与长度，不打印凭据）。
→ 结论：服务器现在确实接受这组凭据，而 App 送出去的**不是同一个字符串**。

代码侧复核（都排除了）：`ConnectionRepository.save` 只加密一次、`revealSecret` 用 UTF-8 原样还原、
`sftpConfig(password = secret)` 不 trim、`SftpChannelPool` 用 `setPassword(bytes, UTF_8)`、
host key 校验失败会走另一条消息（不会伪装成认证失败）。

因此把矛头指向**输入环节**（真机上是圆点显示，看不出来）：
1. 密码框改用密码键盘并关闭自动大写/纠错；账号框同样关闭（中文输入法会把 `Qwe980221` 变成全角）；
2. 密码框加「显示 / 隐藏」开关——全角字符、首尾空格一眼可见；
3. 校验里对"含全角字符 / 密码首尾空格"点名提示（只提示，不改写密码）；
4. 「测试一下」结果标明**用的是哪份密码**（新输入 / 已保存），失败时给出"重输一遍再测"的自检路径。

## 5.3 真机反馈：加连接后回不到本地目录 / 本地目录要手写（2026-10-03，0.1.7）

用户原话：「添加了连接之后，无法访问本地目录了，而且在增加连接处，选了本地目录还要手写目录路径，
并且我授权全部目录也还需要手写路径」。三个问题同一片区域，逐条查清：

1. **回不到本地目录**：`publishRoot()` 的口径是"远端优先"（`remoteRoot ?: localRoot`），
   所以一旦有连接设为当前，本地目录就只是备胎；而界面里 `ConnectionsViewModel.clearCurrent()`
   虽然早就写好，**却没有任何 UI 调用它** → 用户无路可退。修：连接页「本地目录」卡片在远端生效时
   直接给「改用本地目录（取消当前连接）」按钮，并在切换后给一句提示。
2. **本地目录要手写**：LOCAL 协议只让用户手打绝对路径。修：编辑器里给
   「选择目录」（SAF 选择器，结果以 URI 写进地址）、「使用内部存储」（一键填 `/storage/emulated/0`，
   未授权时引导去开「所有文件访问」）、「用已选的目录」（沿用当前全局本地根）。
   SAF 选择器由 :app 提供（`pendingSafTarget` 区分"给编辑器"还是"给全局根目录"两个消费者）。
3. **口径不一致（真正的坑）**：界面上那个标着「本地目录（绝对路径）」的输入框绑的是 **basePath**，
   而 `:app` 的 `applyLocalConnectionRoot` 读的是**地址里的 host** —— 用户认真填了却不生效。
   修：本地连接**只保留地址里的那一个目录字段**，根路径字段对 LOCAL 隐藏，校验也不再校验 basePath。
   顺带把 LOCAL 的路径校验放宽到两种合法形态（`content://` 树 URI 与绝对路径）。

测试：`:feature:connections` 新增 1 例（SAF/绝对路径合法、相对路径给出可照做提示、LOCAL 不再被 basePath 拦下）。

## 5.4 真机反馈：一播 MP4 就闪退 + 要排序（2026-10-03，0.1.8）

用户原话：「实测，一播放视频 mp4 就闪退了 / 增加文件文件夹排序功能，视频播放进度保存功能，

**闪退先解决"看得见"**：自用 sideload 拿不到 logcat，用户只能描述"闪退了"，
所以这一版先把**崩溃证据采集**做齐（0.1.8）：

2. `AppLog` 增加**内存环形缓冲**（按行拆分、超长截断、只留最近 400 行）——出事前的现场往往比堆栈更能说明问题；

## 5.5 两处闪退的兜底（2026-10-03，0.1.9）

用户追加反馈：「通过模型生成字幕，开始操作时也会闪退」——**两个不同功能在"开始操作"时都闪退**。

排查顺序与结论：
1. **先排除 native 页对齐**：解包 release APK 的 `lib/arm64-v8a`，逐个 `llvm-readelf -l` 看 LOAD 段对齐，
   再用 build-tools 的 `zipalign -c -P 16` 校验 zip 条目 —— **19 个 .so 全部 ✅ 16 KB**（含 ffmpeg-kit、
   whisper/ggml、VLC、libc++_shared），这条排除；
2. **再查"异常会不会冒到默认处理器"**——两处都有这个结构性问题：
   - 字幕前台服务的 `CoroutineScope(SupervisorJob() + Dispatchers.Default)` **没有 CoroutineExceptionHandler**，
     识别链路上的 JNI / ffmpeg 解码 / 写文件任何一处抛出未捕获异常，都会冒到线程默认处理器 → **整机闪退**；
   - 播放页 `open()` 里 setMedia / prepare / play **在 try 之外**，内核抛异常同样直接冒出去。
3. 修法（0.1.9）：给字幕服务加 `CoroutineExceptionHandler` + 整个识别循环 try/catch（异常 → 该任务记
   `ENGINE_UNAVAILABLE` + 通知里写原因 + 停服务）；播放页把装载与起播、会话绑定、字幕同步分别兜底
   （装载失败 → 播放页错误卡片 + 中文原因）。测试：:feature:player-video +1（假内核注入 setMedia 抛异常 →
   必须进 ERROR 状态而不是抛出去）。
4. **仍未定位根因**：真正的崩溃原因要靠 0.1.8 起自带的崩溃采集（Java 处理器 + ApplicationExitInfo 补抓原生异常）
   ——待用户复现后回传设置页「诊断与崩溃日志」全文。

## 5.7 「开始生成字幕就闪退」根因定位（2026-10-03，0.1.12）

**用户回传的诊断卡截图给出了完整栈**（这是 0.1.8 加的崩溃采集第一次发挥作用）：

```
android.os.Parcel.createException(Parcel.java:3398)
android.os.Parcel.readException(Parcel.java:3381)
android.app.IActivityManager$Stub$Proxy.setServiceForeground(IActivityManager.java:8059)
android.app.Service.startForeground(Service.java:862)
io.github.gua123.mediagate.app.AsrForegroundService.onCreate(SourceFile:66)
android.app.ActivityThread.handleCreateService(ActivityThread.java:6324)
```

日志顺序同时佐证：[启动] → [恢复字幕队列 3 项] → 崩。即**服务是被系统在后台拉起的**
（`AsrForegroundService` 当时返回 `START_STICKY`，且清单 `stopWithTask="false"`）。

**报告头部（用户第二张截图，即上一张的上半部分）**：

```
时间：2026-10-02 06:58:06
版本：0.1.9（versionCode 10）
包名：io.github.gua123.mediagate
设备：Xiaomi 25102RK69C / Android 17（SDK 37）
线程：main (id 2)

== 异常 ==
java.lang.RuntimeException: Unable to create service io.github.gua123.mediagate.app.AsrForegroundService
  at android.app.ActivityThread.handleCreateService(ActivityThread.java:6335)
```

要点：外层是 ActivityThread 的包装异常（"`Unable to create service <服务名>`"＝**服务的 onCreate 抛了**），
内层原因正是另一张截图里的 `setServiceForeground → Parcel.readException`（AMS 拒绝前台化）。
**另一条重要事实：用户的真机是 Android 17（SDK 37）**——比 targetSdk(36) 更新，
前台服务类型限制只会更严，不会再松。

**根因**：Android 14/15+ 对前台服务类型有"启动时机"限制——`mediaProcessing` 类型**不允许从后台进入前台**
（`Service.startForeground` → AMS `setServiceForegroundInner` 抛
`ForegroundServiceStartNotAllowedException`，经 Parcel 回传给客户端）。于是后台被拉起 → `onCreate`
立刻前台化 → 被拒 → 服务崩 → 进程闪退。

**修法（0.1.12）**：
1. `onStartCommand` 返回 **`START_NOT_STICKY`**（不再被系统在后台重启；队列状态在 Room 里，
   下次进 App 显示「已中断，可续跑」）；
2. `onCreate` 记 `foregroundReady`，失败即 `stopSelf()`；`onStartCommand` 见未前台化就直接退场
   （同时避开"startForegroundService 未按时 startForeground"这条崩溃路径）；
3. `AsrQueueController.startService` 返回成败，失败时把队列停在「已暂停」并把异常写进日志。

**口径确认**：用户从 App 内点「开始/继续」时 App 必在前台，前台化合法 ✓ 后台/息屏继续跑不受影响。

## 7. 真机验收反馈与修复（2026-10-02，提交 `1a3b693`）

## 8. 真机验收反馈与修复（二）：明文 http 被系统策略拦死（2026-10-02，提交 `0af4e6a`）

**根因**：清单里既没有 `android:usesCleartextTraffic` 也没有 `android:networkSecurityConfig`。
Android 9（API 28）起 **targetSdk ≥ 28 的应用默认禁止明文流量**，本应用 targetSdk 36 →
真机上 OkHttp / HttpURLConnection 对任何 `http://` 地址都会直接抛
`CLEARTEXT communication to ... not permitted by network security policy`。
而局域网那台 WebDAV 正是 `http://192.168.1.10:8080`（第 0 章的实测结论），**等于 WebDAV 在真机上全挂**。
1264 个 JVM 用例跑在 JVM 上、不受系统网络策略约束，所以一个都抓不到——与第 7 节 SFTP 接线同类的
"真机才暴露"缺口（已并入 M9 修复）。

**修复内容**：
1. 新增 `app/src/main/res/xml/network_security_config.xml`：`base-config cleartextTrafficPermitted="true"`
   ＋信任系统根证书；「要不要走明文」仍由两层把关——连接页的 per-连接开关 `allowInsecureHttp`，
   以及 `WebDavConfig` 在 scheme=http 且开关关闭时直接拒绝构造；
2. 清单挂上 `android:networkSecurityConfig`；
3. 新增 `CleartextPolicyTest`（:app，2 例）做回归护栏：清单必须挂配置、配置必须放开明文——
   这条以后被子代理改回去会立刻红。

**证据**：app 模块 10 例（+2）0 失败；全项目 `testDebugUnitTest --rerun-tasks --no-build-cache`
**1274 例 0 失败**（第 7 节修复后的 1272 + 本节 2 例）；`:app:assembleDebug` / `:app:assembleRelease` 通过；
aapt2 在 release 包内可见 `xml/network_security_config`（资源压缩后为 `res/8G.xml`，引用仍在清单里）；
dist/ 交付包更新为 74,186,126 B，SHA-256 `1ff62c85…39285c`，V2 签名不变。

**真机截图确认（2026-10-02，用户提供）**：连接页上 WebDAV 卡片显示的正是本条根因——

    homedev · WebDAV · 1 个地址 · 不可用（当前）
    DNS 0 ms · TCP 15 ms · 握手 1 ms · 合计 16 ms
    网络不可达 ❌（当前网络到不了这个地址（局域网 IP 在蜂窝下通常不可达））
    网络不可达：UnknownServiceException CLEARTEXT communication to 192.168.1.10 not permitted by network security policy

TCP 15 ms 就通了，说明网络没问题——是明文被系统策略拦住；而卡片把它说成「网络不可达」、
提示里还整段英文。据此又补一处修正（提交 `3f78b65`）：`ConnectivityError` 新增
`CLEARTEXT_BLOCKED`（「明文流量被系统拦截」＋「打开允许明文 http 或改用 https」），
`fromThrowable` 认 CLEARTEXT、`fromMessage` 认「明文」，都排在其他规则之前；
WebDAV probe 异常不再统一加「网络不可达：」前缀（IOException 交给 `ErrorText` 归类，
兜底「网络请求失败」）。同页 SFTP 卡片为「正常（DNS 0 / TCP 20 / 握手 460 ms）」，说明握手链路本身没问题。
