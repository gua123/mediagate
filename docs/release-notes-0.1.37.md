## mediagate 0.1.37 —— 缓冲能不能"多线程"？能，但要分两件事

### 先说清一件事：**同一时刻的播放字节必须按顺序到达**

所以"同一段数据开几个线程一起读"并不会让播放更快——播放器要的是第 N 个字节接着第 N-1 个。
真正能提速的是另外两件：**提前取**（预读）与**并发取块**（把一大段拆成多条连接同时拉）。

### 这一版做了什么

| # | 做法 | 为什么快 |
| --- | --- | --- |
| 1 | **段内并发取块**：4 MB 的段拆成 4 个 1 MB 的 Range 请求**同时发**（并发上限 4） | 公网高延迟链路里，多个请求把往返延迟"藏"起来；也不再受单条 TCP 连接的窗口限制 |
| 2 | **预读后 2 段**：读到某段后，后台把后面两段也拉进缓存 | 播放推进到那里时数据已在本地，直接省掉等待 |
| 3 | 保留原有：**4 MB 分段 + LRU 淘汰 + 同一段单飞**（不重复下、绝不留下半截段） | 省流量、失败不留脏数据 |
| 4 | 并发上限 **4**（手机连接数/服务端都有限，开太大反而互相拖慢） | 稳 |

### 验证（这次也写了实证单测）

- `SegmentChunksTest`：拆块边界（首尾相接、末块可短、0/负数不拆、块大小兜底）——4 例；
- `SegmentedCacheBackendTest` 新增一例：**用 4 MB 段跑一次读，断言"确实出现了并发"**（记录的并发峰值 ≥ 2），
  并校验读出来的字节正确 ⇒ 不是"写了一堆 async 就算完"，而是真的并发且数据对。

### 想更快还能调

段大小（4 MB）、块大小（1 MB）、并发块数（4）、预读段数（2）现在都是内部默认值；
如果你的链路是"单连接被服务端限速"那种，把并发调到 6–8 会更明显——需要的话我做成设置项。
