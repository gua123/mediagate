# 方案：加载提速、缓存保留 5 个、设置页精简

> 2026-10-28 应你要求「加载还是慢，能否用 Go 写多线程加载模块；设置页清理不可用/旧设置；缓存改为播完 5 个后在第六个删除第一个，但加载足够快才改」而写。
> **本轮只出方案，不改代码**；确认后再做。

## 0. 结论先行

1. **不建议把 Go 模块接进 App**。goroutine 和 Kotlin 协程是同一类 IO 等待模型；真正瓶颈通常是服务器/链路 RTT、连接数上限、段粒度和预取目标。Go 还会引入 JNI、native 崩溃、无法 JVM 单测、重复协议/缓存等问题。
2. **先用 Kotlin 做有优先级的并行加载器**：播放请求 > seek 落点 > 预读 > 下一集；按后端能力限制并发；动态调 2–4 路。
3. **「缓存后续播放进度」现在有真实缺口**：已有 PlaybackProgressStore 存了每个文件的位置，但打开文件时 prefetchHead() 仍按 position=0 预取（只抓头/尾），续播点没预取。先补这个，收益最直接。
4. **5 个视频缓存保留**可以做，但加「加载足够快」闸门：先观察最近 3 次播放的首帧/seek/卡顿，达标才启用；不达标保持现有 LRU/大小上限，默认不改行为。
5. **设置页确实有几处过期/误导**：段大小入口、4/8 GB 快捷档、预读 2 段旧文案、网络分组副标题、后台保活里的字幕生成残留。逐项列在 §5。

## 1. 先量什么（不改行为）

用设置 → 诊断与日志里已有的数据：

| 指标 | 看什么 | 判断 |
| --- | --- | --- |
| 首帧 | 冷缓存/热缓存分开 | 冷慢查网络/预取；热慢查解码/本地 IO |
| seek 到出画 | 拖到 50% 再回拖 | 高查段粒度/落点/连接 RTT |
| 缓存命中率 | 0.1.82 诊断卡 | 低查预取目标，不是并发 |
| 卡顿 | Media3 loading 事件 | 高且吞吐低查链路/服务器限速 |

需要你配合一次：同一视频、同一条连接，记录「首次打开 / 已缓存打开 / 拖到 50%」三组首帧与 seek 时间。没有这组数，Go/多线程值不值只能猜。

当前能力：4 MB 段、段内 4×1 MB 并发、滑窗 4 段×2 连接、自适应预读；SFTP 通道池上限 4，WebDAV 走 OkHttp。

## 2. Go 模块评估（结论：不做生产模块）

| 维度 | Go（gomobile/JNI） | 现有 Kotlin |
| --- | --- | --- |
| 并发 | goroutine 与协程同类，不是魔法 | 协程 + Dispatchers.IO |
| 协议 | 要重接 SSH/SFTP、HTTP、FTP；鉴权/TOFU/选路重做 | WebDAV/SFTP/FTP 已有 |
| 缓存 | 全部走 Go（重写缓存）或每块 JNI 往返 | 已有段缓存/预取/统计 |
| 测试 | 只能真机/native 测 | 1300+ JVM 用例 |
| 包体/ABI | 增加 Go runtime 与 ABI，16 KB 页对齐重验 | 无新增 |
| 崩溃面 | native 崩溃、线程生命周期、JNI 引用 | 已有崩溃采集 |

Go 不会绕过服务器/线路的并发上限。**如果你仍想验证**：只做 2–3 天离线 POC（开发机用 Go 对同一文件跑 1/2/4/8 路并发读取，和 Kotlin 同条件比），不进 App；数据出来再决定。

## 3. Kotlin 并行加载器（推荐）

- **请求分级**：PLAYBACK > SEEK_TARGET > READ_AHEAD > NEXT_EPISODE。
- **每后端并发上限**：min(caps.maxParallelReads, 上限)；SFTP=4，WebDAV 按 OkHttp，FTP 独立数据连接，不硬编码。
- **按段单飞**：同一段已有 in-flight 就复用，避免重复请求。
- **动态并发**：最近 3 次吞吐高且无卡顿 → 加 1 路（到上限）；下降/卡顿 → 减 1 路；默认保守 2 路。
- **播放与预取隔离**：播放请求优先；预取低优先级，可暂停新预取，不杀已在写的任务。
- **可立刻试**：prefetchAhead 的 2 连接改为按后端上限；优先加「不同段」并行，不把单段切更碎；播放与预取用不同 SFTP Channel。

不在本轮：重写成 64 KiB 块表；没有数据证明 4 MB 段是瓶颈前不做。

## 4. 缓存后续播放进度

现状缺口：

- PlaybackProgress 已按 backendId + path 存 positionMs；
- prefetchHead(path) 调 warmUpForOpen(path) 时 position=0，只预取头/尾；
- 播放器自己 seek 到续播点后才发请求 ⇒ 续播第一段仍等网络。

改法：

1. prefetchHead 异步读 playbackProgress.load(backendId, path)：
   - 有位置且有时长 ⇒ warmUpForOpen(path, positionMs, durationMs)，预取续播点所在段 + 往后 30 秒；
   - 时长未知 ⇒ 只预取头/尾，不瞎猜。
2. PlaybackProgress 增加 durationMs（旧记录按 0 迁移），否则 openPlan 无法按比例算落点。
3. 播放中每 5–10 秒/暂停/退出保存位置（现有保存点不够密就补节流保存），不额外发网络请求。
4. 预取目标：续播点前 1 段 + 后 2 段（防回拖）+ 头部（moov），按文件大小裁切。
5. 验收：续播首帧少等一个 RTT 量级；无位置/时长时与现在一致。

## 5. 设置页精简

### 5.1 删除/调整

| 位置 | 现状 | 处理 |
| --- | --- | --- |
| 网络与缓冲 → 段大小 | 1/2/4/8 MB chips | 从主设置移除，内部固定 4 MB（基准最优）；旧值按默认迁移；要保留只放诊断/高级 |
| 缓存上限快捷档 | 0/128/256 MB/1/2/4/8 GB | 快捷档改 0/128/256/512 MB/1/2 GB；4/8 GB 去掉（自定义仍可到 8 GB） |
| 预读段数 | 0–4 滑杆 | 改名「预读上限」，说明自适应只往下收；默认 4 不变 |
| 恢复默认文案 | 「默认 4 MB 段 · 预读 2 段」 | 改为「4 MB 段 · 自动预读（上限 4 段）」（当前文案是错的） |
| 网络分组副标题 | 「预读 / 段大小 / 缓存上限与已用量」 | 改为「预读上限 / 缓存保留 / 已用量」 |
| 后台保活说明 | 多处「批量字幕生成」 | 字幕已删，改为「后台播放/下载」 |
| 诊断卡注释 | 仍提 VLC/旧引擎 | 清掉用户可见旧名词，只留 Media3 |
| NetworkTuningSection 注释 | 「四项参数：并发块数/块大小...」 | 删掉不存在的两项 |
| CacheTuning.READ_AHEAD_CHOICES | 未使用的旧档位 | 删除或只留 UI 实际用的值 |

### 5.2 保留

- 播放缓冲 3/5/10/20/30 秒；
- 画中画、控制层自动隐藏、后台保活；
- 缓存明细、清空、自定义缓存上限；
- SFTP 主机密钥、更新、诊断；
- 缓存上限可输入（你明确要的精确控制）。

### 5.3 新增

- 网络分组加只读状态：「缓存保留：最近 5 个视频（未达标，暂不启用）/ 已启用」；
- 诊断卡缓存行补「保留策略 / 已保留视频数」。

## 6. 播完 5 个删第 1 个（带快速闸门）

规则：

- 维护最近播放视频列表（path + backendId + 时间 + 是否看完/观看时长），只记视频。
- 第 6 个开始播放时，若加载足够快：取最旧、非当前、非 pinned 的一个，异步删除整份自动缓存；列表保持 5 个；重复播放只移到最前。
- **手动缓存/pin 永不删**；建议不占 5 个名额。
- 缓存上限/LRU 仍在；5 个策略是额外上限，不替代。

「加载足够快」闸门（可调，先观察 3 次）：

- 首帧 ≤ 1.5 s；
- seek 到出画 ≤ 1.0 s；
- 卡顿 0；
- 缓存命中率 ≥ 50%。

满足 → 下一次第 6 个视频开始时启用删除；不满足 → 继续 LRU/大小上限，不动旧缓存；诊断卡显示为什么没启用。

需要确认的边界：

1. 「播放完」按看完（≥90%）还是看过 30 秒？后者更符合缓存最近看过的。
2. pin/手动缓存是否占 5 个名额？建议不占、永不删。
3. 闸门阈值用这组还是等 P0 实测。

## 8. 验收

- 同文件/网络：首帧、seek、卡顿不劣于 0.1.83；有改善记录数字；
- 续播：有进度时首帧明显快于只预取头/尾；
- 5 个策略：第 6 个开始时最旧自动缓存被删，当前/最近 5 个/pinned 保留；不达标不删；
- 设置页：保留项实际生效；删除项无残留入口；旧偏好不崩；
- 全量 JVM 用例 + 真机复验；不新增 native ABI。
