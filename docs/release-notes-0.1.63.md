## mediagate 0.1.63 —— 首次打开更快：预取"真正要读的地方"

### 上次为什么没解决

0.1.53 的"打开即预取"**只抓了文件开头两段**。但很多视频（尤其非 faststart 的 MP4）把**索引 moov 放在文件末尾**——播放器一打开就得先读最后那一段才能算出时长与关键帧，所以"开头预取"对它一点帮助都没有，你还是得等。

另一个漏掉的地方：**续播**。你上次看到 40 分钟，这次点开播放器会跳到 40 分钟处读数据，而预取的是开头，要等的那一段仍要现拉。

### 这一版三处改进

1. **同时抓两头**：首段（起播数据）+ **尾段**（moov / 索引用），两个请求并行，不阻塞起播；
2. **续播 / 拖拽落点也预取**：没有 TS 索引的普通视频用「字节偏移 ≈ 位置 / 时长 × 文件大小」估算（码率基本恒定，够用），把"跳过去要读的那一段"提前拉下来；
3. **宁可不动也不瞎猜**：文件大小或时长拿不到时**直接跳过**预取（不会把请求打到错误的偏移上）。

换算逻辑抽成了带单测的纯函数（PrefetchTargets.tailOffset / offsetForPosition）。

### 如果还是很慢，帮我确认两件事

- 这个文件是不是 **.ts**？（TS 会先扫描一段做索引，那是另一条路径——若是它，我下一步就优化扫描策略）
- 是**局域网**还是**公网**？公网约 600 ms 的往返延迟下，首段的等待主要来自延迟而不是带宽。
