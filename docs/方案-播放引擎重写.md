# 方案：把视频播放引擎换掉（语言选型 + 分阶段路线）

> 2026-10-06 应你要求「使用合适的编程语言重写视频播放引擎，先给出方案」而写。
> **本文只是方案，不动代码**；你拍板后我再开工。

---

## 0. 先说结论（一句话）

**不建议"整体重写"，建议"内核可插拔 + 自研 FFmpeg 内核"**：
语言上，**引擎内核用 Rust（次选 C++）**，JNI 边界与业务层继续用 Kotlin。
理由在 §3、§4 展开；这条路每一步都能单独交付、能真机验收、能随时回退。

---

## 1. 现状：现在的"引擎"到底是什么

| 层 | 现在用什么 | 谁在控制 |
| --- | --- | --- |
| 解复用 / 解码 | Media3 1.11.1（ExoPlayer）内部 Extractor + MediaCodec 硬解 | **黑盒**（我们只能选解码器档位） |
| 兜底内核 | LibVLC 3.7.6（JNI + 我们自研回环 HTTP 代理） | 半黑盒；**这台机器上它一初始化就把进程带走**（已由面包屑 + 独立进程探针证实） |
| 渲染 | 交给 Media3 / LibVLC 的 Surface 输出 | 黑盒 |
| 音视频同步、缓冲、seek | Media3 内部（TS 的 seek 是它自己的二分查找） | 黑盒 |
| 数据来源 | **我们自研**：`StorageBackend → RandomAccessSource` + 分段缓存 + 超时层 | 自己的 |
| 会话 / 通知栏 / 画中画 / 字幕 | 我们自研（MediaSession、字幕解析与渲染在我们这边） | 自己的 |

**关键事实**：真正"卡脖子"的只有中间那一层（解复用/解码/渲染/同步）；数据层、会话层、字幕层、UI 层都是我们自己的，**换引擎不需要动它们**——这也是当初把它们抽象出来的目的。

---

## 2. 为什么要换（把动机说清楚，避免为了重写而重写）

已知的具体痛点，按严重程度：

1. **LibVLC 在这台机器上必崩**（原生崩溃，独立进程探针判定 FAILED）⇒ 兜底内核实际不可用，等于"只有 Media3 一条腿"。
2. **Media3 不吃我们的格式/协议细节**：.ts 的精确 seek 只能靠它内部实现，我们的时间↔字节索引只能用于"预取"而**不能真正接管 seek**（不能宣称毫秒级拖拽）。
3. **解码档位不自由**：Media3 只支持"硬解优先/强制软解"这种粗粒度；要加"特定编码强制软解""解码器黑名单"这类能力，它给不了。
4. **音频能力受限**：音量 >100% 要靠 `LoudnessEnhancer` 补丁；均衡器、声道处理、精确音量曲线都要绕。
5. **出问题查不动**：崩溃在 Media3/系统 codec 内部时，我们只能兜底降级，拿不到细节。

如果你的动机是上面某几条，方案 A 就够；如果是"我想要一个完全自己掌控、性能极限优化的播放器"，那才需要方案 B。

---

## 3. 语言选型

| 语言 | 适合做引擎的理由 | 代价 | 结论 |
| --- | --- | --- | --- |
| **Rust** | 内存安全（音视频代码最容易野指针）、cargo/NDK 交叉编译现代、FFmpeg 有 `ffmpeg-next`/`rsmpeg` 绑定、渲染可用 `wgpu`/OpenGL ES 绑定、生态有 `symphonia` 等纯 Rust 解码器 | FFmpeg 绑定要跟版本、**JNI 胶水要自己写**、Android 音视频的现成例子比 C++ 少；调试成本比 Kotlin 高 | ✅ **首选**（长期维护最省心） |
| **C++** | FFmpeg 是一等公民、Android NDK 支持最好、几乎全部现成播放器（VLC/ijkplayer/mpv）都是它，能大量参考 | 内存安全全靠自觉、构建复杂（CMake/NDK/ABI）、崩溃更难查 | ✅ 次选（"照着 mpv/VLC 抄"时最快） |
| **Kotlin / Java** | 与现有工程零摩擦，MediaCodec/Media3 直接可用 | 只能建在 MediaCodec 之上，**拿不到 FFmpeg 那种格式与协议覆盖**；真要做 demux 得自己从零写 | ⚠️ 只适合"薄封装 + 业务"这一层 |
| **Go** | 写并发舒服 | 音视频生态弱、cgo 边界麻烦、NDK 支持差 | ❌ 不推荐 |
| **Python / Dart 等** | — | 性能与平台支持都不合适 | ❌ 不做 |

**推荐组合**：`Kotlin（UI/会话/数据层） → JNI 薄封装 → Rust 引擎（demux/decode/render/sync）→ FFmpeg + MediaCodec/AAudio/OpenGL ES`。

---

## 4. 三条路线

### 方案 A（推荐）：内核可插拔 + 自研 FFmpeg 内核

- 在现有 `PlayerEngine` 抽象下**新增第三种内核** `FfmpegEngine`（Rust 实现），
  与 Media3 并列可选：**Media3 = 默认硬解（日常够用、功耗低）**，**FFmpeg = 万能兜底**（替换掉现在必崩的 LibVLC）。
- 引擎内部：FFmpeg 负责 demux/解码（或只做 demux + 交给 MediaCodec 硬解），
  视频输出用 OpenGL ES（`SurfaceTexture` → 渲染到我们现有的 Surface），音频用 AAudio/AudioTrack；
  seek 直接吃我们**已有的时间↔字节索引** ⇒ 终于能做到"按索引落点、毫秒级"。
- 增量：先"只换兜底内核"，验证稳定后再考虑把默认内核也换过去（那时可做成"经典模式/新引擎"开关）。
- 工作量：**约 15–25 人日**（分 4 个里程碑，见 §5）；风险可控，每一步都能回退到现在的行为。

### 方案 B：整体重写为 Rust 播放器

- 把 Media3 也一起换掉，全自研 demux/decode/render/sync + TS/MP4/MKV 全格式。
- 收益：完全掌控、格式覆盖最大、性能上限最高、许可与体积更干净（APK 可能反而变小，去掉 libvlc 与 Media3 的部分）。
- 代价：**数月量级**、期间要维持两条播放路径、字幕/会话/画中画都要重新对齐；出问题没有"另一个内核"可以退。
- **只有在"方案 A 跑通且明显不够用"时才建议进入。**

### 方案 C：不换语言，只补痛点

- 保留 Media3，把能修的修掉：禁用/隔离 LibVLC 崩溃路径（已有探针）、
  把 TS seek 做成"我们给 Media3 喂自定义 SeekMap"（需 fork `TsExtractor`）、音量/亮度已有自己的实现。
- 收益：风险最低、几天就能有结果；代价：仍然受 Media3 黑盒限制，"自己写引擎"的诉求达不到。

---

## 5. 方案 A 的里程碑（每步可交付、可真机验收）

| 里程碑 | 内容 | 验收标准（客观可测） |
| --- | --- | --- |
| **M1 骨架** | Rust crate + `cargo-ndk` 交叉编译进 APK；JNI 边界；能"打开一个本地文件并把第一帧画到 Surface" | 本地 MP4 起播成功；`unsigned char*` 帧数据到屏幕可见；构建全绿 |
| **M2 播放** | 解复用 + 音视频同步 + 播放/暂停/seek；接我们自己的 `RandomAccessSource`（远端也能播） | 局域网 WebDAV 的 MP4 能播、能拖拽；音画同步偏差 < 80 ms（主观 + 打点日志） |
| **M3 兜底内核** | 作为"第三内核"接入播放页（内核徽标多一档），替换 LibVLC 的位置 | **不再有原生崩溃**（探针+面包屑验证）；切内核不崩、不丢进度 |
| **M4 覆盖与调优** | .ts 索引接管 seek、软解档位、字幕对接、画中画/后台播放对齐 | TS seek 落点命中率 ≥ 95%；后台播放 30 分钟不中断；耗电不高于 Media3 的 1.5× |

> 每个里程碑都做**真机验收**（你的手机），不通过就不进下一步。

---

## 6. 风险与对策

| 风险 | 对策 |
| --- | --- |
| Rust + FFmpeg + Android 的坑比较多（绑定版本、ABI、Surface 互操作） | 先做"能出画面"的最小骨架（M1）再谈其他；绑定锁版本 |
| 新的原生库又出现"一初始化就崩" | **一开始就复用现有独立进程探针机制**（`:probe` 进程 + 面包屑），并且默认不启用新内核，用户手动切才加载 |
| APK 体积与 16 KB 页对齐 | 复用现有 `llvm-readelf`/`zipalign` 核对脚本（历史上已做过 19 个 .so） |
| 两条内核的体验分裂（功能对不上） | 把"内核能力差异"显式写在界面上（哪一档支持什么），不做静默降级 |
| 时间成本 | 方案 A 分里程碑，任何一步停下来都不影响现有版本可用 |

---

## 7. 需要你拍板的三件事

1. **动机**：你最想解决的是哪一个——(a) LibVLC 崩溃/兜底不可用、(b) 大 .ts 拖拽不够准、(c) 想要完全自研掌控、(d) 其它（说一下现象）。
2. **路线**：方案 A（换兜底内核，15–25 人日）/ 方案 B（整体重写，数月）/ 方案 C（不换语言，打补丁）。
3. **语言**：Rust（我推荐）/ C++（照着 mpv 抄最快）。

> 我的建议：**先按方案 A + Rust 做 M1（1–3 天，只求"能出第一帧"）**。
> M1 一跑通，后面每一步都是增量；跑不通我们再回到方案 C，沉没成本极小。
