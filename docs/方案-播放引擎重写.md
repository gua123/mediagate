# 方案：把视频播放引擎换掉（语言选型 + 分阶段路线）

> 2026-10-06 应你要求「使用合适的编程语言重写视频播放引擎，先给出方案」而写。
> **本文只是方案，不动代码**；你拍板后我再开工。

## 0. 先说结论（一句话）

> ⚠️ **2026-10-06 用户拍板，方向已定**：
> 「视频引擎只采用一套，不要来回切换，自研一套视频播放引擎，尽可能适合全部视频文件类型」。
> ⇒ **§4 的三条路线与 §7 的选项作废**（不再做"第三内核/可插拔"那套）；
> 当前唯一口径与已完成的进展见文末 **§9**。

**不建议"整体重写"，建议"内核可插拔 + 自研 FFmpeg 内核"**：
语言上，**引擎内核用 Rust（次选 C++）**，JNI 边界与业务层继续用 Kotlin。
理由在 §3、§4 展开；这条路每一步都能单独交付、能真机验收、能随时回退。

## 1. 现状：现在的"引擎"到底是什么

| 层 | 现在用什么 | 谁在控制 |
| --- | --- | --- |
| 解复用 / 解码 | Media3 1.11.1（ExoPlayer）内部 Extractor + MediaCodec 硬解 | **黑盒**（我们只能选解码器档位） |
| 兜底内核 | LibVLC 3.7.6（JNI + 我们自研回环 HTTP 代理） | 半黑盒；**这台机器上它一初始化就把进程带走**（已由面包屑 + 独立进程探针证实） |
| 渲染 | 交给 Media3 / LibVLC 的 Surface 输出 | 黑盒 |
| 音视频同步、缓冲、seek | Media3 内部（TS 的 seek 是它自己的二分查找） | 黑盒 |
| 数据来源 | **我们自研**：`StorageBackend → RandomAccessSource` + 分段缓存 + 超时层 | 自己的 |
| 会话 / 通知栏 / 画中画 / 字幕 | 我们自研（MediaSession、字幕解析与渲染在我们这边） | 自己的 |

**关键事实**：真正"卡脖子"的只有中间那一层（解复用/解码/渲染/同步）；数据层、会话层、字幕层、UI 层都是我们自己的，**换引擎不需要动它们**——这也是当初把它们抽象出来的目的。

---

## 2. 为什么要换（把动机说清楚，避免为了重写而重写）

已知的具体痛点，按严重程度：

1. **LibVLC 在这台机器上必崩**（原生崩溃，独立进程探针判定 FAILED）⇒ 兜底内核实际不可用，等于"只有 Media3 一条腿"。
2. **Media3 不吃我们的格式/协议细节**：.ts 的精确 seek 只能靠它内部实现，我们的时间↔字节索引只能用于"预取"而**不能真正接管 seek**（不能宣称毫秒级拖拽）。
3. **解码档位不自由**：Media3 只支持"硬解优先/强制软解"这种粗粒度；要加"特定编码强制软解""解码器黑名单"这类能力，它给不了。
4. **音频能力受限**：音量 >100% 要靠 `LoudnessEnhancer` 补丁；均衡器、声道处理、精确音量曲线都要绕。
5. **出问题查不动**：崩溃在 Media3/系统 codec 内部时，我们只能兜底降级，拿不到细节。

如果你的动机是上面某几条，方案 A 就够；如果是"我想要一个完全自己掌控、性能极限优化的播放器"，那才需要方案 B。

## 3. 语言选型

| 语言 | 适合做引擎的理由 | 代价 | 结论 |
| --- | --- | --- | --- |
| **Rust** | 内存安全（音视频代码最容易野指针）、cargo/NDK 交叉编译现代、FFmpeg 有 `ffmpeg-next`/`rsmpeg` 绑定、渲染可用 `wgpu`/OpenGL ES 绑定、生态有 `symphonia` 等纯 Rust 解码器 | FFmpeg 绑定要跟版本、**JNI 胶水要自己写**、Android 音视频的现成例子比 C++ 少；调试成本比 Kotlin 高 | ✅ **首选**（长期维护最省心） |
| **C++** | FFmpeg 是一等公民、Android NDK 支持最好、几乎全部现成播放器（VLC/ijkplayer/mpv）都是它，能大量参考 | 内存安全全靠自觉、构建复杂（CMake/NDK/ABI）、崩溃更难查 | ✅ 次选（"照着 mpv/VLC 抄"时最快） |
| **Kotlin / Java** | 与现有工程零摩擦，MediaCodec/Media3 直接可用 | 只能建在 MediaCodec 之上，**拿不到 FFmpeg 那种格式与协议覆盖**；真要做 demux 得自己从零写 | ⚠️ 只适合"薄封装 + 业务"这一层 |
| **Go** | 写并发舒服 | 音视频生态弱、cgo 边界麻烦、NDK 支持差 | ❌ 不推荐 |
| **Python / Dart 等** | — | 性能与平台支持都不合适 | ❌ 不做 |

**推荐组合**：`Kotlin（UI/会话/数据层） → JNI 薄封装 → Rust 引擎（demux/decode/render/sync）→ FFmpeg + MediaCodec/AAudio/OpenGL ES`。

## 4. 三条路线

### 方案 A（推荐）：内核可插拔 + 自研 FFmpeg 内核

- 在现有 `PlayerEngine` 抽象下**新增第三种内核** `FfmpegEngine`（Rust 实现），
  与 Media3 并列可选：**Media3 = 默认硬解（日常够用、功耗低）**，**FFmpeg = 万能兜底**（替换掉现在必崩的 LibVLC）。
- 引擎内部：FFmpeg 负责 demux/解码（或只做 demux + 交给 MediaCodec 硬解），
  视频输出用 OpenGL ES（`SurfaceTexture` → 渲染到我们现有的 Surface），音频用 AAudio/AudioTrack；
  seek 直接吃我们**已有的时间↔字节索引** ⇒ 终于能做到"按索引落点、毫秒级"。
- 增量：先"只换兜底内核"，验证稳定后再考虑把默认内核也换过去（那时可做成"经典模式/新引擎"开关）。
- 工作量：**约 15–25 人日**（分 4 个里程碑，见 §5）；风险可控，每一步都能回退到现在的行为。

### 方案 B：整体重写为 Rust 播放器

- 把 Media3 也一起换掉，全自研 demux/decode/render/sync + TS/MP4/MKV 全格式。
- 收益：完全掌控、格式覆盖最大、性能上限最高、许可与体积更干净（APK 可能反而变小，去掉 libvlc 与 Media3 的部分）。
- 代价：**数月量级**、期间要维持两条播放路径、字幕/会话/画中画都要重新对齐；出问题没有"另一个内核"可以退。
- **只有在"方案 A 跑通且明显不够用"时才建议进入。**

### 方案 C：不换语言，只补痛点

- 保留 Media3，把能修的修掉：禁用/隔离 LibVLC 崩溃路径（已有探针）、
  把 TS seek 做成"我们给 Media3 喂自定义 SeekMap"（需 fork `TsExtractor`）、音量/亮度已有自己的实现。
- 收益：风险最低、几天就能有结果；代价：仍然受 Media3 黑盒限制，"自己写引擎"的诉求达不到。

## 8. 能不能"App 本体一种语言、内部另一种语言"？（2026-10-06 追问）

**能，而且这正是 Android 上的主流做法**（VLC、mpv、ijkplayer、ExoPlayer 的扩展全是这么干的）。
但"哪些部分值得下沉、哪些不值得"要分开看——**下沉不是免费的**，每跨一次语言边界就多一层
调试成本、崩溃风险和构建复杂度。

### 8.0 先把话说准：我们现在的"App 本体"是 Kotlin，不是 Java

- **Kotlin 和 Java 编译成同一种字节码、跑在同一个 ART 上、互相调用零成本**，对性能与"标不标准"没区别；
- 但**我们的界面是 Jetpack Compose，而 Compose 只能用 Kotlin 写**（官方不支持 Java）⇒
  "App 本体用 Java"意味着**把整套界面重写成 View 体系**，这是纯倒退、没有收益；
- 如果你说的"用 Java"是指"外面这层用标准 Android 语言就行"——那**现在就是**（Kotlin 是 Android 官方首选语言）；
- 如果你有别的考虑（比如自己要在 Android Studio 里改、或担心 Kotlin 生态），说一声，我按你的理由再评估。

### 8.1 分层建议（哪些下沉、哪些不下沉）

| 模块 | 现在 | 建议 | 为什么 |
| --- | --- | --- | --- |
| **视频引擎**（demux/解码/渲染/同步） | Media3 / LibVLC 黑盒 | ✅ **下沉到 Rust/C++**（FFmpeg + MediaCodec + GLES/AAudio） | 收益最大：摆脱两个黑盒、TS 精确 seek、解码档位自由、崩了能查 |
| **读取文件**：字节搬运 / 缓冲 / 预读 | Kotlin（`SegmentedCacheBackend` + 协议后端） | ⚠️ **部分下沉**：native 侧做"直通式读取与缓冲"（拿到 fd/socket 直接喂解码器，省掉 Kotlin→JNI 逐帧拷贝）；**协议适配与配置仍留 Kotlin** | 逐帧数据过 JNI 是最贵的；但协议实现重写一遍没有收益 |
| **连接模块**（增删改查 / 凭据 / 测连通） | Kotlin（Room + Keystore + 中文错误） | ❌ **不下沉** | 低频操作、不是瓶颈；Keystore 加密、Room 落库、文案中文化、权限都在 Android 侧——搬过去只是把简单事做复杂 |
| **传输实现**（HTTP/SFTP/FTP 字节流） | OkHttp / JSch | 🔶 **可选，第二阶段** | 只有当"逐帧拷贝"实测成为瓶颈时才值得 |
| **字幕 / 会话 / 通知 / 画中画 / 设置** | Kotlin | ❌ **不下沉** | 全是 Android 平台能力，native 里做等于重新发明一遍 |

一句话分工：**Kotlin 管"策略与平台"（谁的连接、什么权限、怎么存、怎么显示），native 管"字节与像素"（搬得快、解得快、画得快）。**

### 8.2 JNI 边界的四条硬规矩（不遵守一定踩坑）

1. **边界要"粗"不要"细"**：传句柄 / fd / 直接 ByteBuffer / Surface，**绝不逐帧传数组或对象**——
   每帧一次 JNI 调用加一次拷贝，能把省下的性能全吃回去，还多一堆崩溃面；
2. **native 不碰 Android SDK**：Keystore、Room、通知、权限、Activity 生命周期一律留 Kotlin；
   native 只拿 Surface/fd/路径；反过来 Kotlin 也不窥探 native 内部状态；
3. **错误要能翻回中文**：native 只回**错误码 + 结构化信息**，文案仍由 Kotlin 侧统一生成
   （否则界面里会冒英文堆栈——这是我们早定过的红线）；
4. **崩溃可见性优先**：native 崩了 Java 的 UncaughtExceptionHandler **抓不到** ⇒ 新模式一开始就复用现有三件套：
   独立进程探针（:probe 进程）+ 面包屑（同步写盘）+ 崩溃错误页；新内核**默认不启用**，手动切才加载。

### 8.3 迁移顺序（每步都能停在可用状态）

| 步骤 | 内容 | 完成判据 |
| --- | --- | --- |
| **①** Rust 骨架进 APK | cargo-ndk 交叉编译 + 一个 JNI 函数 + 能读 fd 把第一帧画到 Surface | 真机出画面；构建全绿；.so 16 KB 对齐 |
| **②** 引擎接上我们的数据源 | native 通过 fd/句柄读**我们已有的分段缓存**（不重写协议） | 局域网 WebDAV 的 MP4 能播、能拖 |
| **③** 顶替 LibVLC | 作为"第三内核"接入内核徽标 | 不再有原生崩溃；切内核不丢进度 |
| **④**（可选）字节路径下沉 | 若实测"拷贝"是瓶颈，再把缓冲/预读搬进 native | 起播与拖拽延迟相对 ③ 有可测改善 |

### 8.4 代价（必须知道的）

- **构建变慢、工具链变长**：NDK + Cargo/CMake，报错跨语言，本地与 CI 都要能重编 .so；
- **调试难度上一个台阶**：native 崩溃要看 tombstone / ndk-stack，不能再靠 JVM 单测兜底；
- **两套语言 = 两套纪律**：unsafe 边界、内存所有权、线程模型都要写进项目规则；
- **但这一切只在"确实要自己掌控引擎"时才值得付**——若你更在意稳定省心，方案 C（不换语言、只打补丁）依然成立。

## 9. 最终方向：**一套自研引擎**（2026-10-06 用户拍板）

> 用户原话：「**视频引擎只采用一套，不要来回切换，自研一套视频播放引擎，尽可能适合全部视频文件类型**」

### 9.1 定下来的架构

- **只有一套引擎**：`mediagate-engine`（C++17），住在 `:media:engine-native` 模块里；
- **"硬解/软解"是它内部的两条解码路径，不是两个引擎**：`MediaCodec（硬解优先） → FFmpeg（软解兜底）`，
  对用户永远是同一个引擎、同一个内核徽标，**没有"切换内核"这个动作了**（那一栏将来删掉，改成显示当前解码路径）；
- **格式覆盖靠 FFmpeg**：MP4/MKV/TS/M2TS/FLV/AVI/WMV/RM/WebM… 的解复用与解码全部交给 FFmpeg，
  我们自己做渲染、音视频同步、缓冲与 seek；
- **边界**：`PlayerEngine` 契约不变（这正是当初把它抽象出来的目的）——数据层、会话层（通知栏/画中画）、
  字幕层、UI 层**一行都不用动**。

### 9.2 语言：选 **C++17**（不是 Rust）

| 理由 | 说明 |
| --- | --- |
| 与 FFmpeg 的亲和度 | FFmpeg 本身就是 C 库；C++ 直接调 API，Rust 要维护一层绑定（版本对不上就编不过） |
| 工具链已就绪 | NDK r30 + CMake 4.1.2 已在 `.toolchain`，C++ 这条链路**本机已实测跑通**（见 9.4） |
| 资料密度 | 出问题时能对着 ijkplayer/mpv/VLC 的现成实现与海量问答定位；Rust 侧同类资料少一个量级 |
| 代价 | 内存安全要自己守（我会把"谁释放、谁拥有"写进项目规则，并用 ASan/valgrind 思路做本地检查） |

（Rust 依然可行、更安全，但要额外承担绑定与构建成本，起步工作量约 +30%；**你若更看重内存安全，说一声我换**。）

### 9.3 里程碑（每一步都能真机验收）

| 里程碑 | 内容 | 验收标准 |
| --- | --- | --- |
| **M1 骨架 ✅ 已完成** | 模块 + CMake + JNI + Kotlin 薄封装；只回答"我是谁、什么版本、内部有哪几条解码路径" | 构建全绿、`.so` 进 APK、16 KB 页对齐、JNI 符号导出、契约护栏测试（**均已实测通过**，见 9.4） |
| **M2 出画面** | 链接 FFmpeg；解复用 + 解码 + 渲染到我们现有的 Surface | 本地 MP4/MKV 能出画；TS 也能出画 |
| **M3 能播** | ① 连续视频播放（帧循环 / 播放暂停停止 seek）✅<br>② 音频（AAudio）+ 音视频同步 ✅<br>③ 接我们的 `RandomAccessSource`（自定义 AVIO 回调进数据层）✅ | 「局域网 WebDAV 的 MP4 能播、能拖；音画偏差 < 80 ms」**要等 M4 接进播放页后才能在真机上验**（引擎侧三条都已就绪） |
| **M4 接管播放页** | ① 适配层：`NativeEnginePlayer` 实现 `PlayerEngine` + 能力矩阵 ✅<br>② 界面入口：内核三档轮转 + 能力提示 ✅（2026-10-15）<br>③ 默认改走自研引擎 **待真机验过** | 日常片源全部由自研引擎播放；无内核切换动作 |
| **M5 覆盖与调优** | 覆盖矩阵打满 + 硬解路径 + TS 精确 seek + 字幕/画中画对齐 | 见 9.5 的覆盖矩阵与性能基线 |

### 9.4c M3 进展（2026-10-15）

**① 连续视频播放（上半，提交 `a3dc53e`）**：`native_player.{h,cpp}` —— 一条工作线程跑帧循环，
解复用 → 解码 → **按帧 pts 节流送屏**（睡眠切成 ≤200 ms 小片，随时响应暂停/seek/停止），
支持 play / pause / resume / stop / seekTo（`av_seek_frame(..., AVSEEK_FLAG_BACKWARD)` + `avcodec_flush_buffers`）。
**这一版只播画面，没有声音。**

**② 音频 + 音画同步（下半，本回合）**：自研引擎"能播"了——**有声音，而且音画对齐**。

| 环节 | 做法 | 为什么这么做 |
| --- | --- | --- |
| 音频输出 | **AAudio 回调模式** + 自研 1 秒 PCM 环形缓冲（`audio_output.{h,cpp}`） | 视频解码偶尔卡一下不会立刻把声音饿死；回调是实时线程 ⇒ 里面只有原子量 + memcpy，不加锁不分配不打日志 |
| 音频解码 | FFmpeg 解码 → **libswresample 统一重采样成 48 kHz 双声道 float** | 输出格式固定 ⇒ 设备/片源怎么变，时钟换算只有一条路径 |
| 音画同步 | **音频时钟＝AAudio "已播出帧数" ÷ 采样率**；视频帧比时钟早就在小片睡眠里等，迟到 > 120 ms 直接丢帧 | 音频做主轴是播放器通行做法（人耳对声音断续最敏感）；丢帧比音画错位好看 |
| 时钟锚定 | 缓冲一空就把"媒体时间 ↔ 设备帧计数"重新锚定一次 | 欠载 / seek 之后的误差不会累积，能自己纠回来 |
| seek | 丢光未播音频 + 丢重采样器残留 + 时钟搬到目标位置 + 目标点之前的帧全丢 | 否则"拖完进度条会先响一段旧声音" |
| 暂停 | 音频设备一起按停 | 时钟跟着冻结 ⇒ 继续播不会瞬间追帧（老的挂钟实现会"快放"一段） |
| 时间轴 | 新增 `Timeline`：pts 按流的 `start_time` 归一，没有就用第一帧兜底 | **TS/MPEG 的 pts 常常不从 0 开始**，不归一第一帧会被判成"还早"、白等一大截 |
| 没有音频 / 音频打不开 | 退化成"播放挂钟"当主轴；音频失败只记中文原因（状态里的"音频输出说明"）继续放画面 | 纯视频文件照样播；音频设备被占用不该把整个播放拖死 |

**③ 接我们的数据层（AVIO 回调，本回合）**：引擎不再只会 `fopen` ——
FFmpeg 的读/seek 通过 JNI 回调到 Kotlin，落回全项目唯一的那个数据抽象
（`StorageBackend → RandomAccessSource`）。**这一步做完，本地 / SAF / WebDAV / SFTP / FTP
对引擎就是同一条路**（分段缓存、超时层、预取也全都还在链路上）。

| 环节 | 做法 | 为什么这么做 |
| --- | --- | --- |
| 数据来源 | Kotlin 接口 `NativeMediaSource`（`length` / `read` / `lastError`）+ `RandomAccessMediaSource` 适配器 | 引擎不该知道"文件"是什么；它只会要"第 N 字节起的 M 个字节" |
| 挂起 → 阻塞 | 适配器里用 `runBlocking` 包住 `RandomAccessSource.readAt` | native 的播放线程本来就该在这里等；数据层内部自己切 IO 调度器 |
| 零拷贝进解码器 | `NewDirectByteBuffer` 包住 FFmpeg 给的缓冲再交给 Kotlin | 读 32–64 KB 一次，**不能**再多一次 Java 堆拷贝；用完记得 `DeleteLocalRef`（非方法调用不会自动回收） |
| native 线程回调 | `JNI_OnLoad` 存 `JavaVM` ⇒ 播放线程按需 `AttachCurrentThread`，线程退出时 `DetachCurrentThread` | 播放线程是 native 自己建的，JVM 不认识它；attach 一次就够（thread_local 记录） |
| 出错可读 | 读失败 → `lastError()` 取回**中文**原因，写进播放错误（"读取数据出错：…"） | 库/网络抛的英文 message 不能直接进界面（单语红线）；也避免"播着播着停了"这种没头没尾的表现 |
| seek | 我们本来就是随机访问 ⇒ seek 只做位置换算（`resolveSeekPosition`，纯函数） | `AVSEEK_SIZE` 如实回长度；长度未知时不瞎猜，回 `ENOSYS` 让 FFmpeg 自己退化 |

### 9.4d M4 上半：自研引擎接进 `PlayerEngine` 契约（2026-10-15）

契约本身不动（这正是当初抽象它的目的），新增的只有一个**能力矩阵**：

| 件 | 说明 |
| --- | --- |
| `NativeEnginePlayer`（`:media:engine-native`） | 实现 `PlayerEngine` 的 13 个动作。**播放逻辑一行都不在这里**——它只做"翻译"：契约动作 ↔ JNI 调用、native 状态串 ↔ `EngineState` |
| 数据从哪来 | prepare 时按 `MediaSourceRef` 取当前 `StorageBackend` → 开 `RandomAccessSource` → 交给引擎 ⇒ 本地 / SAF / WebDAV / SFTP / FTP 同一条路（分段缓存、超时层都在链路上） |
| 画面挂哪 | 自研引擎自己的 `SurfaceView`；**数据源与画面两件事都到齐才起播**（native 要求先有 Surface），`surfaceDestroyed` 就解绑 ⇒ 不会画到野指针上 |
| 状态 | 250 ms 轮询 native 状态串 → `EngineState`（纯函数 `NativeEngineStateMapper`：六个状态逐条钉死）；位置 / 时长另走便宜入口（只读原子量，界面与字幕覆盖层可以随便问） |
| 能力矩阵 | 契约里新增 `EngineCapabilities`：自研引擎**如实声明** 倍速 ✗ / 解码档位 ✗ / 缩放四档 ✓ / 音量 >100% ✓（软件增益，会削波）。旧内核不覆盖该属性 ⇒ **默认全支持，不引入行为变化** |
| 缩放四档 | native 侧 `scaleTarget`（纯函数）算送屏缓冲多大：FIT 取小（留黑边）、CROP 取大（超出由送屏裁掉）、STRETCH 直接铺满、ORIGINAL 原样 —— **四条路共用同一条送屏路径** |
| 结束态 | native 新增 `PlayerState::ENDED`：播完画面停在最后一帧，seek 之后回到播放中 |
| 容器 | `AppContainer.createEngine` 多一个 `EngineKind.NATIVE` 分支；`EngineSelection.fallbackFrom(NATIVE)` → Media3（过渡期它打不开就退到默认内核，**不静默**） |

**证据（都不需要真机）**：JNI 导出 **21 个**（新增音量 / 缩放 / 位置 / 时长 4 个）；宿主单测 **118 项断言**；
全量 **1548 用例 0 失败**。新增两条源码级护栏并**实证可失败**：
① `ResizeMode` 的 ordinal 必须与 native `ScaleMode` 的**数值**一一对应 ——
第一版护栏只比名字，把 CROP / STRETCH 的数值对调照样能过，已加固成逐个核数值（这类"看起来在护栏其实没护住"的坑值得单独记一笔）；
② 新增能力矩阵不许改变旧内核行为（默认全支持）。

### 9.4f M4 收尾：独立进程探针 + 自动回退 + 诊断可见（2026-10-15）

自研引擎**第一次跑在用户的机器上**之前，把三件"保护性"的事做完：

| 件 | 做法 | 为什么 |
| --- | --- | --- |
| **独立进程探针** | `NativeEngineProbeService` 跑在 `:engineprobe`（与 LibVLC 探针同一套）：先写 `start` → 调 `nativeSelfCheck()`（**真开一次 H.264/AAC 解码器 + swscale/swresample + **AAudio 开流写 100 ms 静音**）→ 写 `ok` 或 `fail`（中文原因）→ 写 `done` | 自研引擎最容易"把进程带走"的就是 FFmpeg 解码器初始化与 AAudio 开流；放在独立进程里，崩了只带走探针自己，主进程据此**拦住切换**并给「重新测试」 |
| **打开失败自动回退** | 内核报错且当前是自研引擎 ⇒ **自动换回 Media3** 继续播，并弹一句说明（"自研引擎播不了这个文件（原因），已自动换回 Media3 继续"）；**每个文件只做一次** | 口径"不硬切、不静默"：用户不需要动手，但要知道为什么换了内核；只做一次是避免画面来回跳 |

### 9.4h 真机第一次试播：切不过去（2026-10-15，0.1.66 → 修复）

用户装了 0.1.66 预览包，点内核轮到「自研引擎」，**画面立刻退回 Media3**。他把面包屑发来，一眼定位：

```
10-15 21:51:09 切换内核：→ 自研引擎（已释放旧内核）
10-15 21:51:09 切换内核：新内核已创建 自研引擎
10-15 21:51:09 切换内核：开始恢复现场（装载媒体）
10-15 21:51:09 切换内核：现场恢复完成
10-15 21:51:09 切换内核失败：自研引擎 → Failed to resolve SessionToken for ComponentInfo{…VideoPlaybackService}.
                Manifest doesn't declare one of either MediaSessionService, …
10-15 21:51:09 自研引擎播不了 → 自动回退 Media3
```

**两条根因（都不在引擎里，而在"接线"上）**：

1. **清单少了会话 action**：视频后台播放服务 `VideoPlaybackService` 没声明
   `androidx.media3.session.MediaSessionService`。Media3 的 `SessionToken(context, ComponentName(...))`
   会用 `queryIntentServices` 按三个 action 反查服务的**类型**（MediaSessionService / MediaLibraryService /
   MediaBrowserService），一个都没声明就抛 `IllegalArgumentException`。音频那个服务从 M1 起就有这个 action，
   视频这个从 M8-A 起就没有——**也就是说视频的通知栏/锁屏控制其实一直没连上**，只是从来没人发现
   （起播那条路把异常吞了，只写日志）。
2. **附属失败被当成内核失败**：换内核那段没兜住这个异常 ⇒ 自研引擎被判成「这个文件播不了」⇒
   触发了 9.4f 做的自动回退 ⇒ 用户看到的现象就是「切了又跳回来」。

**修法**：① 清单补 action（`exported=false` 保持不变——同应用、非导出也查得到，权限最小）；
② 会话绑定的兜底从**两处调用点**收进 `bindSession` **一个函数**（起播 / 换集 / 换内核全覆盖，将来新增调用点也自动安全），
失败只记日志 + 面包屑：**会话是附属能力，连不上不算播放失败**。

**这次事故换来三条护栏（都实证过"破坏就能红"）**：

- `:app` 的 `SessionServiceDeclarationTest`：扫源码里所有 `SessionToken(..., ComponentName(..., X::class.java))`，
  逐一核对清单里那个服务**必须有会话 action**（横跨两个文件的交叉约束，编译器与 Lint 都不管）；
- `:feature:player-video` 的「会话绑不上不该让换内核失败」：注入"连不上会话"，断言换内核仍然成功、不回退；
- **修掉一个护栏假绿**：Gradle 原来判定测试 UP-TO-DATE 直接跳过（清单不是测试输入）⇒ 破坏清单后测试照样"绿"。
  现在 `:app` 把 `src/main/java`、`src/main/res`、`src/main/AndroidManifest.xml` 声明成 Test 输入。
  同一个坑当场还暴露了第二层：护栏最初按"服务名第一次出现"抓清单块，结果抓到了注释里提到的名字 ⇒ 往前抓到
  音频服务那段（它带着 action）⇒ 又假绿一次；改成按 `android:name` 属性锚定后才真红。

**教训一句话**：**新能力第一次上真机时，先怀疑"老接线"（清单/权限/会话/服务），再怀疑新代码**——
这次引擎本身一路跑到了"现场恢复完成"，是旁边那根从来没被真正验证过的线把它绊倒的。

### 9.4g 播放指标可见（2026-10-15，网络加载方案 P0.4 落地）

"变快没变快、卡没卡"必须有数，否则一切优化都是感觉。这一版把指标摆到用户能截图的地方：

| 指标 | 谁量的 | 口径 |
| --- | --- | --- |
| **起播耗时** | native（第一帧送屏那一刻结算） | 从播放线程开始（含打开数据源）到第一帧 blit 成功 |
| **seek 等待** | native | 从 seek 请求到落点第一帧送屏 |
| 丢帧 / 音频欠载 / 音画偏差 | native（已有） | 同步逻辑里顺手记的 |

- 契约新增 `PlayerEngine.metricsLine()`（默认 null ⇒ 旧内核不用改）；
  自研引擎把它拼成一行中文：「起播 380 ms · seek 等待 120 ms · 丢帧 0 · 音频欠载 0 · 音画偏差 -12 ms」；
- 播放页**每个文件上报一次**（`VideoPlayerEnvironment.reportPlaybackMetrics`），宿主留最近 5 条；
- 设置页诊断卡新增「最近播放：…」一栏（带时间戳，等宽字体，可复制/另存/分享——复用的是诊断卡原有的三个出口）。

**证据**：状态串字段 13 → 15（老串缺字段也照样解析，有单测）；全量用例与产物见本轮提交说明。

**证据**：全量 **1569 用例 0 失败**（31 模块，新增 11 例：探针判据 / 诊断文案 / 界面拦截 / 自动回退）；
JNI 导出 **22 个**（新增 `nativeSelfCheck`）；源码级护栏钉住"探针必须声明在独立进程 `:engineprobe` 且真的调自检"
（少写 `android:process` 就变成在主进程里跑最危险的那几步，而构建与单测都不会报错）。

### 9.5 覆盖矩阵（M5 的验收标准）

容器：MP4/M4V、MKV/WebM、TS/M2TS、FLV、AVI、MOV、WMV、MPG、RM/RMVB（尽力）；
视频编码：H.264、H.265/HEVC、VP9、AV1（软解兜底）、MPEG-2/4、VC-1、WMV3、RealVideo（尽力）；
音频编码：AAC、MP3、AC3/EAC3、DTS（尽力）、FLAC、Vorbis、Opus、PCM；
协议：本地 / SAF / WebDAV / SFTP / FTP（全部走我们已有数据层）；
字幕：外挂 srt/vtt/ass 保持现状；内嵌字幕（MKV）在 M5 评估。

### 9.6 风险与对策（**一套引擎＝没有第二套可退**，所以这几条是硬要求）

1. **过渡期不硬切**：M2–M3 期间自研引擎只在"我的片源它打不开"时才不接管；M4 起默认走它，
   但**只要它明确不支持某文件**，就回退旧路径并在界面上说明原因（用户不需要手动选，这一步由代码判断）；
2. **M5 覆盖矩阵达标后**，把 Media3/LibVLC 两条旧路径**整条删除**（模块、依赖、内核徽标、切换逻辑），
   真正做到"只采用一套"；
3. **崩溃可见性照旧**：native 崩溃 Java 处理器抓不到 ⇒ 继续用独立进程探针 + 面包屑 + 崩溃错误页；
4. **不再发"骨架版"给你**：按发版纪律，骨架不可感知就不发版（`0.1.64` 之后的下一个正式版，
   会等到 M2/M3 有**看得见的效果**时才发）。
