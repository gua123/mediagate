## mediagate 0.1.44 —— 给「慢」装一把尺子，并按你给的数字做了两处针对性优化

### 你的数据我读成这样

| 场景 | 实测 |
| --- | --- |
| 本软件 · 公网 WebDAV | **0.1 MB/s** |
| 本软件 · 公网 SFTP | **0.9 MB/s** |
| 其它软件 · 公网 WebDAV | 慢 |
| 其它软件 · 公网 SFTP | **1 MB/s / 3 MB/s** |
| 你的公网上传 | ≈15 MB/s（远没吃满） |

关键线索是那条 **600 ms 的连接耗时**（连接测试里"握手"那段）——**每个网络请求都要先等约 0.6 秒才开始来数据**。
于是：

    有效速度 ≈ 块大小 ÷（往返延迟 + 块大小 ÷ 单连接带宽）

| 块大小 | 600 ms 延迟下的理论上限（单连接 5 MB/s） |
| --- | --- |
| 512 KB | ≈0.4 MB/s |
| 1 MB | ≈0.7 MB/s |
| 2 MB | ≈1.2 MB/s |
| **4 MB** | **≈1.9 MB/s** |

⇒ 这正好解释了两件事：**① 你的 SFTP 0.9 MB/s 就是"1 MB 块 + 600 ms 延迟"的结果**；
**② 加线程（并发 4→8）几乎没用**，因为瓶颈是"每次请求的等待"，不是"连接不够多"。
**真正有效的方向是"减少请求数"：块越大越快。**

### 这一版做了什么

1. **SFTP 去掉每次读都做的 `stat`**：以前每取一个 1 MB 块都要先问一次文件大小（+1 个往返），
   公网 600 ms 延迟下等于白扔四成速度；现在按路径缓存属性（128 条 LRU）；
2. **块大小新增 4 MB**：一个 4 MB 段只用 1 个请求 ⇒ 往返次数降到最低；
3. **内置测速**：**设置 → 网络与缓冲 → 测速**，填一个远端文件路径（相对连接根目录），
   点「开始测速」→ 用真实播放路径读 8 MB → 报 **MB/s + 当时的设置**，结果可整段复制发我。

   （提示：测**没播放过**的文件最准；已缓存的段不走网络。）

### 建议你这样试（每次都能用测速量出来）

| 试法 | 说明 |
| --- | --- |
| 块 **4 MB** + 并发 **1** | 最省往返：单连接、每段一个请求 |
| 块 **4 MB** + 并发 **2** | 两条连接各拉 4 MB，看是否翻倍 |
| 块 **1 MB** + 并发 **4**（默认） | 对照基线，应当明显更慢 |

把三组数字发我，我就能判断你的链路到底是"延迟主导"还是"服务器单连接限速"，
然后把默认值改成你这个环境下最快的组合。
