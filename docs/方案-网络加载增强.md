# 方案：网络加载视频更快（**不计带宽**，只谈"更快就绪、且不打扰播放"）

> 2026-10-14 应你要求「app 中通过网络加载视频文件需要增强，先忽略网络带宽的因素，只从更快的加载视频文件，不影响播放这方面给出一个方案」而写。
> **本文只是方案**，你点头后按 P0 → P1 → P2 分批做。

---

## 0. 先把"更快"拆成三件事（不然容易白忙）

带宽不变的前提下，"更快"只可能来自这三处：

| 方向 | 含义 | 对用户的感觉 |
| --- | --- | --- |
| **A. 更少的往返** | 握手、stat、探测这些"不搬数据但要走一趟"的请求，能省则省、能合则合 | 点开就有反应（不是转圈） |
| **B. 更早开始取** | 在用户"还没点"的时候就把开头/索引拿到手 | 点开几乎不用等 |
| **C. 更准地取** | 一次就取对地方（首帧、索引、续播点、下一个关键帧），不拉无关字节 | 拖动/续播不再干等 |

**"不影响播放"是硬约束**：任何预取都必须**给正在播放的请求让路**（可暂停、可取消、可降优先级），
并且**永远不占用播放所需的段**——这条不做，预取越多越卡。

---

## 1. 现状（已经有的，别重复造）

- 分段缓存（4 MB 段、按段单飞、预读 2 段、按连接命名空间、文件指纹过期护栏、上限可调）；
- **打开即预取**（首段 + 尾段 + 续播落点）、`PrefetchTargets` 纯函数换算；
- 超时层（元数据 15 s / 读 30 s）+ 中文错误 + 重试；
- SFTP 的 `stat` 已有 LRU 缓存（不再每块白付一个 RTT）。

**还缺的**：没有优先级/抢占、预取是"盲目两段"而不是"按索引精确取"、连接与解码器没有并行预热、
列表页不做任何预热、也没有可观测的指标。

---

## 2. 方案（按性价比排序，P0 先做）

### P0 真机结论（**2026-10-15 用户确认**）

> 用户原话：「**刚刚测试下来，新文件加载明显变快了**，亮度和音量的调整也都正常了」。

已落地的两件（都进 0.1.6x 预览包）：**打开即预取**（首段 + 尾段 + 续播落点，按"消费方第一个请求落在哪个字节"定目标）
与**打开文件夹自动缓存**（单文件按段并发 4、一次 2 个文件、用户一操作就让路）＋**列表封面空闲预热**（并发 2，取到即刷新那一格）。
用户能明显感觉到差别 ⇒ **P0 这条线的"更早开始取"验收通过**（判断标准就是他自己那句"明显变快了"，不靠我自证）。

同一条回复里也确认了**亮度/音量手势**（分层实现：亮度落窗口、音量 0–100% 走内核、>100% 走系统音效链）在真机正常。

**仍待做**：P0 里的可观测指标（起播耗时等，✅ 已进诊断卡）、请求优先级与抢占的显式化；P1（按索引精确取、滑窗预取、下一集预热）；P2（字节路径下沉，与自研引擎合并做）。

### P0：把"该省的往返"省掉、把"预取让路"做成硬约束（预计收益最大、风险最低）

1. **请求优先级 + 抢占**（`storage-api`）
   - 取数请求带优先级：`PLAYBACK`（正在播的段）> `SEEK_TARGET`（刚落点）> `PREFETCH`（预取）；
   - 同一时刻只有 `PLAYBACK` 能占满连接；预取在播放请求到来时**主动暂停/让出**，播放请求完成后再续；
   - 预取任务**可取消**（切集、退出、seek 都会取消过期的预取）。
2. **合并与复用"小请求"**
   - HTTP：连接池 + keep-alive（同一连接连续取段，省掉每次 TCP/TLS 往返）；
   - SFTP：**会话与通道复用**（现在是每次 openRead 建通道，改为池化），`stat` 已有 LRU，再补 `readdir` 结果短缓存；
   - WebDAV：`PROPFIND` 结果按目录短缓存（列表页来回切不重复请求）。
3. **解码器与取数并行预热**（引擎侧）
   - 现在顺序是"等到数据 → 建解码器 → 起播"；改成**一确定要播就同时**做：解析容器头（首段/尾段）+ 实例化解码器 + 准备 Surface；
   - 收益：MediaCodec 配置那 100–300 ms 被藏进等待数据的时间里。
4. **可观测指标（否则无法证明变快了）**
   - 打点三个数：**起播耗时**（点开到第一帧）、**seek 等待**（拖到出画）、**卡顿次数/时长**；
   - 落在诊断卡里可复制（用户能把它发我）。

### P1：从"盲目预取两段"升级为"按索引精确预取"

5. **先拿索引，再按索引取**
   - MP4：解析 `moov`（首段或尾段已预取）⇒ 得到关键帧表、时长、码率；
   - TS：用我们已有的时间↔字节索引；
   - MKV：解析 cues/seekhead（有则用，没有则退化为按比例估算）；
   - 有了索引，seek/续播就是"取那一段"而不是"先取再找"。
6. **滑窗预取（跟着播放位置走）**
   - 以当前位置为基准，前向预取 N 段（N 由设置里的"预读段数"控制），**已缓冲够就停**；
   - 回退/前进后重新规划窗口，旧窗口的未完成预取立即取消。
7. **"下一集/上一集"预热**
   - 当前集播到 80% 且列表里确实有下一集时，只取下一集的**头部元数据（几 KB～首段）**；
   - 收益：连播时切集几乎瞬时；代价极小（可被取消）。

### P2：把字节路径下沉到引擎（与"自研引擎"合并做）

8. **native 直读缓存文件**：引擎直接 `open` 分段缓存里的段文件（或直接 fd），省掉 Java 侧逐块读 + JNI 拷贝；
9. **内存映射/预分配**：段文件预分配（避免写放大），热段用 mmap 读；
10. **首帧优先**：先解出第一帧显示，再补音频同步（用户感知的是"画面出来了"，不是"音频对齐了"）。

## 3. 验收标准（客观可测，不靠感觉）

| 指标 | 现状基线 | 目标（同一网络、同一文件） |
| --- | --- | --- |
| 局域网 MP4 起播（未缓存 → 首帧） | 待测（诊断卡打点） | **≤ 1.0 s** |
| 公网 MP4 起播（未缓存） | 待测 | **≤ 2.5 s** |
| 已缓存文件起播 | 待测 | **≤ 0.5 s** |
| 拖动到新位置出画 | 待测 | **≤ 1.2 s** |
| 连播切下一集 | 待测 | **≤ 1.0 s** |
| 预取对播放的影响 | —— | **播放中的段永远不排队**（可用日志证明优先级生效） |

前提：先用 P0.4 把基线测出来（现在只有主观"感觉快/慢"）。

---

## 4. 风险与取舍

- **预取吃满连接**：靠优先级 + 让路解决；这也是本方案第一条要做的事；
- **服务器/协议不支持并发或长连接**：做**能力探测 + 降级**（连不上就退回单请求顺序取，不报错）；
- **索引解析失败**（畸形文件）：一律退化为现在的"按比例估算"，不影响可播性；
- **不要为了"快"牺牲正确性**：任何预取失败只记日志，播放路径照旧。
