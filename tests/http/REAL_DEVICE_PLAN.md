# 真机验证方案（WebDAV 多连接）

依据：`REPORT.md` 的实测数字。目标不是"跑分好看"，是**判定 4 条连接够不够、播放会不会被短请求拖死**。

## 1. 连接开几条、怎么分

| 用途 | 连接数 | 形态 | 依据 |
|---|---:|---|---|
| 播放（LibVLC → 回环代理 → RangeStream） | **1（专用，不共享）** | 一条长 Range GET，seek 时重开 | 长连接在 32 条满载竞争下仍有 3.6 MB/s；专用是为了防短请求排队 |
| 缩略图 / 抽帧 | 2 | 256 KiB Range，短请求 | 32 路并发实测 195–268 ms 完成，2 条足够 |
| 目录 / stat / 探针 | 1 | PROPFIND，串行 | 大目录 PROPFIND 本身 330 ms，是服务端枚举，不是连接问题 |
| （可选）预取 | 复用上面 3 条的空闲，或 +1 | 分段 Range | 若恢复 `prefetchParallel`，按 `maxParallelReads-1` 封顶 |
| **合计** | **4（含预取 5）** | | 4 条 = 上限 95%；8 条 = 97%，抖动 ×3 |

硬上限：**不要超过 8**。OkHttp 侧 `maxRequestsPerHost = 8`，超了只会排队；
16/32 条实测只多 1–3% 吞吐、抖动放大 10 倍。

现有代码已对齐：`WebDavStorageBackend.MAX_PARALLEL_READS = 4`、
`SegmentedCacheBackend.prefetchParallel` 里 `reservedForPlayback = maxParallelReads - 1`。
**本次验证不需要改代码**；如果真机发现播放等短请求，优先把专用连接的语义做实
（播放那条不参与共享池），而不是加总连接数。

## 2. 预期指标（局域网 1GbE + 手机 Wi-Fi）

| 指标 | 预期 | 通过线 |
|---|---|---|
| 单流持续吞吐 | 手机 Wi-Fi 限 20–50 MB/s（服务端单流 58–105） | ≥ 8 MB/s |
| 起播（点击 → 首帧） | 0.5–2 s | < 2 s |
| 播放 5 分钟卡顿 | 0 | 0 次 rebuffer |
| 1 MiB 到达间隔 p95 | 100–250 ms（满载竞争时 350 ms） | < 500 ms |
| seek 首帧（10 次） | 0.3–1 s | p95 < 1.5 s |
| 目录打开（大目录） | 0.4–1 s | < 1.5 s |
| 30 张缩略图出图 | 1–3 s | < 3 s |
| 满载 + 播放并存 | 播放流 ≥ 3 MB/s | 不断流、不降码 |

## 3. 操作步骤

前置：手机与 NAS 同网段、5 GHz Wi-Fi；装待验证的调试包；添加
`http://<LAN_HOST>:<PORT>` + Basic 连接。

1. **单流**：打开最大的 mp4（3 GB 级）。记录起播时间、播放 5 分钟是否卡。
   读 `设置 → 诊断` 里缓存行的「最近 X MB/s」。
2. **并发目录/缩略图**：播放中切到文件浏览器，进缩略图密集目录、快速滚动 30 张。
   观察播放是否中断、缩略图多久出齐。
3. **seek**：进度条前/中/后各拖 3 次 + 随机 1 次，共 10 次，逐个计时（首帧出现）。
4. **满载竞争**：起一个后台缓存下载（大文件），同时播放并 seek 3 次。
5. **长稳**：连续播放 10 分钟，记录卡顿次数与诊断里的吞吐区间。

采集：
- `adb logcat -s storage-webdav AppContainer MediaGateApp`（连接、probe、播放指标）
- 设置 → 诊断 → 「缓存：命中 … · 最近 X MB/s」+「最近播放」两行截图

## 4. 判定

- 全部达到第 2 节通过线 → **通过**，4 连接方案定稿。
- 起播/seek 超线 2 倍 → **不通过**，先看 logcat 是「建连/探针慢」还是「读慢」：
  - 建连慢、15 s 级超时 → 走 SFTP 同类问题（会话/临时通道建立），**不是带宽**；
  - 读慢但连接正常 → 才考虑加连接（4 → 6），并只给缩略图/预取加，播放那条始终专用。
- 卡顿但吞吐达标 → 查短请求并发是否超 4、seek 是否把播放流打断（重开 Range 的时机）。
