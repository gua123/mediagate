# HTTP/WebDAV 多连接叠加带宽：实测报告

日期 2026-11-18 · 测试机 30 核 / 1GbE · 服务端 Apache + Basic（明文 http，支持 Range）
所有数字来自 `tests/http/results/*.csv` 与本文列出的命令输出，未做估算。

## 0. 一句话结论

**能叠加，但只有单连接没打满链路时才有收益。** 这台机器上单连接被 NAS 单流读速限制在
58–105 MB/s，4 条连接就能到 101 MB/s（链路上限 107–111 MB/s 的 95%）；再往上只增抖动。
所以 App 侧 **4 条连接足够**，8 条是上限，16/32 没有意义。

---

## 1. 单连接实测（问题 1）

同一文件发 `Range` 请求、读固定字节：

| 文件 | 缓存状态 | 单连接吞吐 | 说明 |
|---|---|---|---|
| `/home/cms+oracle.zip`（246 MiB） | NAS 页缓存命中 | **96.2 MB/s**（86.0–104.1） | 另有 3 次 64 MiB 整段直读：97.4 / 114.8 / 114.8 MB/s |
| 3GB mp4（demo） | 未缓存 / 磁盘读 | **59.6 MB/s**（58.2–61.8） | 32MiB/流 × 4 轮 |
| 4 个 GB 级 mp4 首次读 96MiB | 冷 | 68–73 MB/s | 随机高位 offset |

- 首字节 13 ms，TCP 建连 <1 ms，1MiB 请求 TTFB 级别开销可忽略。
- 结论：**HTTP 单连接没有应用层限速**；上限由「文件在不在页缓存」和「NAS 磁盘单流读速」决定，
  链路 1GbE 的理论上限是 118 MB/s，实测最高 111.6 MB/s（94.5%）。

## 2. 多连接叠加与拐点（问题 2）

主表：3GB 视频文件（冷/大文件，最接近真实播放），每流 32 MiB，4 轮（第 1 轮预热不计入均值）：

| 并发 | 吞吐均值 (MB/s) | 区间 | 抖动 (墙钟 max−min) | 失败数 |
|---:|---:|---|---:|---:|
| 1 | 59.63 | 58.18 – 61.78 | 32 ms | 0 |
| 2 | 93.41 | 91.43 – 94.67 | 24 ms | 0 |
| **4** | **101.14** | 100.39 – 101.51 | **14 ms** | 0 |
| 8 | 103.75 | 102.61 – 104.49 | 45 ms | 0 |
| 16 | 105.87 | 105.11 – 106.69 | 72 ms | 0 |
| 32 | 106.92 | 106.14 – 107.66 | 137 ms | 0 |

附表：246 MiB 热文件（页缓存命中，每流 48 MiB，5 轮）：

| 并发 | 吞吐均值 | 区间 | 抖动 | 失败数 |
|---:|---:|---|---:|---:|
| 1 | 96.23 | 86.02 – 104.12 | 97 ms | 0 |
| 2 | 108.78 | 108.72 – 108.84 | 1 ms | 0 |
| 4 | 110.41 | 110.22 – 110.54 | 5 ms | 0 |
| 8 | 111.15 | 110.89 – 111.34 | 15 ms | 0 |
| 16 | 111.33 | 111.19 – 111.40 | 408 ms | 0 |
| 32 | 111.59 | 111.29 – 111.77 | 2874 ms | 0 |

（附表 16/32 并发各有一轮触到文件尾被截断，吞吐按实际字节算，不影响结论；主表无截断。）

**拐点 = 4 条**：
- 4 条已达 32 条上限的 94.6%，8 条 97.0%；
- 抖动在 4 条最小（14 ms），8 条起单调变大，32 条 137 ms（≈10 倍）；
- 单流 → 4 流的收益 1.7×（冷文件）/ 1.15×（热文件），说明叠加补的是**磁盘单流读速与 CPU 拷贝**，
  不是协议限制。

对照实验（本地服务，每连接人为限速 8 MB/s，排除链路因素）证明协议层没有并发上限：

    1 连接 8.50 · 2 连接 17.14 · 4 连接 34.01 · 8 连接 67.40 · 16 连接 135.09 MB/s

即：**HTTP 的并发叠加是线性的，直到共享资源（这里是 1GbE 网卡 / NAS 磁盘阵列）成为瓶颈。**

## 3. 与 SFTP 对比（问题 3）

同机器、同文件、同期重测（JSch 2.28.7，每流 8–16 MiB 连续读，256 KiB 读缓冲）：

| 方案 | 吞吐 | 抖动 | 备注 |
|---|---:|---:|---|
| SFTP 1 通道 | 37–85（均值 ~64） | 238 ms | 16MiB/轮 ×5；4KB 读缓冲也有 40.7 MB/s |
| SFTP 1 会话 × 10 通道 | **85.6** | 75 ms | 通道上限实测 10 条（第 11 条 `channel is not opened`） |
| SFTP 20 会话 × 10 通道（200 通道） | **90.1** | — | 建连 17.1 s |
| HTTP 1 连接 | 59.6（冷）/ 96.2（热） | 32 / 97 ms | |
| HTTP 4 连接 | **101.1** | **14 ms** | |
| HTTP 8 连接 | 103.8 | 45 ms | |
| HTTP 16 连接 | 105.9 | 72 ms | |

结论：
1. **HTTP 4 条连接 > SFTP 200 条通道**（101 vs 90 MB/s），抖动还小 5 倍。
2. SFTP 的天花板 ~90 MB/s（200 通道），比 HTTP 的 107–111 MB/s 低一档，说明 SSH 侧
   （加密拷贝 + 每通道窗口）比 HTTP 更早成为瓶颈。
3. ⚠️ **交接的 SFTP 基线复现不出来**：交接值「单连接 2.2 MB/s / 20×10=51 MB/s」，
   今天同机同文件实测「单通道 47.8 MB/s（4KB 缓冲 40.7）/ 20×10=90.1」。
   差 10–20 倍，最可能是当时把「读 4MB + 等 1 秒」的等待、或每 256 KiB 重开一次流的开销
   算进了吞吐。**含义：SFTP 15 秒超时不是带宽问题，别往带宽方向查。**

## 4. 播放是否需要专用连接（问题 4）

两组实验，区别在**请求形态**：

A. 真实播放形态——一条持续 Range GET（LibVLC 经回环代理就是这样读）：

| 场景 | 播放流吞吐 | 1MiB 到达间隔 p50 / p95 / max |
|---|---:|---|
| 空载 | 76.2 MB/s | 12 / 17 / 19 ms |
| 16 条满载竞争 | 7.20 MB/s | 81 / 104 / 131 ms |
| 32 条满载竞争 | 3.62 MB/s | 176 / 356 / 379 ms |

B. 每块一个请求（`openRead` 1MiB/次、缩略图、探针）：

| 场景 | 有效吞吐 | 单块延迟 p50 / p95 / max |
|---|---:|---|
| 空载 | 16.9 MB/s | 47.5 / 81.8 / 133.6 ms |
| 16 条满载竞争 | 2.8 MB/s | 117–312 / 536–758 / **1014–3929 ms** |

结论：**长连接不会被饿死**（TCP 公平分到 1/(N+1)，32 条竞争下仍有 3.6 MB/s，够 4K 直连），
但**短请求在满载时尾延迟会到 1–3.9 秒**，seek / 缩略图 / 目录会卡。
所以 HTTP **同样需要给播放留专用连接**——防的是短请求排队和 seek 重开流，不是防带宽不够。
这也解释了 SFTP 那条教训：池被占满时，播放的 `openRead` 只能排队。

## 5. 小请求基线（真机验收阈值依据）

| 操作 | 延迟 |
|---|---|
| 目录 PROPFIND（115 KB 大目录，Depth:1） | p50 **332–349 ms**，新连接/keep-alive 无差别（服务端枚举为主） |
| 256 KiB Range（新连接） | p50 **16.4 ms**，p95 18.4 ms |
| 32 路 256 KiB 并发（瀑布流） | 墙钟 195–268 ms，单请求 p95 163–218 ms |
| 8 路 256 KiB 并发 | 墙钟 57–178 ms |

偶发一次 2.1 s 尾延迟（9 轮里 1 次，未复现），真机验收用 p95 判定，同时留意单次尖刺。

## 6. 公网 WebDAV

从本机不可达：`nas.example.com` 的 8080 / 8443（以及 2222）TCP 连接全部超时，
无法给出公网数字，不编。
公网场景的判断留给真机；预期与局域网相反——高 RTT 下单连接受 TCP 窗口限制，
**多连接在公网才真正有叠加价值**，届时用 `bench_multi.sh` 复测 4/8/16 即可。

## 7. 真机验证方案

见 `REAL_DEVICE_PLAN.md`。核心：**4 条连接**（播放 1 专用 + 目录/缩略图/预取共享 3），
上限 8（对齐 OkHttp `maxRequestsPerHost = 8`）；局域网预期单流 ≥8 MB/s、起播 <2 s、
seek 首帧 <1.5 s、5 分钟零卡顿。
